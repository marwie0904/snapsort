# Image search design

Date: 2026-10-09
Status: draft, pending review

## Goal

Find media in the library that look like a query image. The query is an image file on disk. Matches come from the vectors the `image_embed` module stored during ingest. A CLI command serves people now, and the same Python function serves the chatbot later.

## Scope

In: `snapsort search` CLI command, `search()` function, score cutoffs, tests.

Out: text search, filters from other modules (objects, people, location), a UI, JSON output, video files as queries, README changes.

## Interface

### CLI

```
snapsort search <image> [--limit 20] [--min-score 0.5]
```

```
0.902  /Users/me/Pictures/1.png
0.873  /Users/me/Movies/clip.mov @ 0:42
```

- One line per media file, sorted by score, highest first. Video lines end with the time of the best-matching frame as `m:ss`.
- No match at or above the cutoff: prints `no matches at or above 0.50`, exit code 0.
- Error (see Errors): message on stderr, exit code 2.
- Near-duplicates: `--min-score 0.95`. There is no separate mode.

### Python (`snapsort/search.py`)

```python
@dataclass(frozen=True)
class Match:
    path: str           # absolute media path, as stored
    kind: str           # "image" | "video"
    score: float        # dot product of unit vectors (cosine), -1 to 1
    ts: float | None    # video: second of the best-matching frame; image: None

class SearchError(Exception): ...

def search(query: Path, data_dir: Path, limit: int = 20, min_score: float = 0.5) -> list[Match]: ...
```

## Behavior

1. Reject a query whose extension is not an image extension (`classify(query) != "image"`), which includes videos.
2. Decode the query with `snapsort.ingest.load_image` and embed it with `ImageEmbed.embed`, the same decoding and preprocessing ingest uses. EXIF rotation and HEIC are handled.
3. Load candidate vectors from `<data_dir>/snapsort.db`: `image_embed` results of media whose `runs` row for `image_embed` has `status = 'done'` and `version` equal to the current `ImageEmbed.version`. This skips vectors left over from an older module version, which would score wrongly against a query embedded with the current version.
4. Score every frame by dot product with the query vector. Each media file keeps its highest-scoring frame, and for videos that frame's `ts`.
5. Drop matches below `min_score`, sort by score descending, return the first `limit`.

- A query that is already in the library shows up at about 1.00. There is no special case for it.
- Search never writes. It opens the database only if the file exists, and only runs `SELECT`s. It does not use `ingest.connect`, which creates the database and schema.

## Score cutoffs

Scores range from -1 to 1 in theory but rarely drop below 0. Measured on 2026-10-09 (24 vectors: 3 webcam screenshots of one person, 20 ffmpeg `testsrc` frames, 1 solid-color photo):

| Pair | Score |
|---|---|
| Unrelated content | 0.03–0.42 |
| Same border and watermark overlay, face grayed out | 0.57–0.70 |
| Same person and room, different moment | 0.80–0.90 |
| Edited copy of the same image (mirrored, darkened 50%) | 0.96–0.99 |

Defaults: `min_score = 0.5` hides unrelated content. For near-duplicates (same photo), use 0.95. Recalibrate both on a real photo library. These numbers come from a mostly synthetic set.

Two limits to design around:

- DINOv2 matches whole scenes, not identity. Shared overlays, borders and rooms raise scores (0.57–0.70 for an overlay alone). "Find this person" belongs to the person detection module's face vectors.
- Very small queries are unreliable. At 62×31 px, the exact source image ranked second (0.673 vs 0.690).

## Model and vector loading

- The model is loaded once per process by a `functools.cache`d helper that returns a set-up `ImageEmbed`. A CLI search pays about 5 s for imports and model load. A long-running chatbot process pays it once.
- Vectors are read from SQLite on every call, so results reflect the latest ingest with no cache to invalidate. At 50k vectors this is about 150 MB. Reading is estimated at under 1 s, and scoring takes 10–50 ms.
- The CLI handles `search` before running module discovery, so a search does not import every module.

## Errors

`search()` raises `SearchError` with a message. The CLI prints it to stderr and exits 2.

| Condition | Message gist |
|---|---|
| Query is not an image extension (video or other) | query must be an image |
| Query missing or not decodable (`OSError` from `load_image`) | cannot read query |
| `<data_dir>/snapsort.db` does not exist | nothing ingested, run `snapsort ingest <path> --modules image_embed` |
| No current `image_embed` vectors | same hint |

## Testing (`tests/search/test_search.py`)

Uses the real model and the shared `sample_image` and `sample_video` fixtures, ingested with `run_ingest` into a temp data dir.

1. The sample image as the query returns itself first, with a score above 0.99, `kind == "image"` and `ts is None`.
2. Querying with the stored frame file of video second 1 returns the video as one row with `ts == 1.0`.
3. `min_score` and `limit`: `limit=1` returns one match, `min_score=1.01` returns none.
4. A media file whose `runs` version is changed to `"0"` is excluded.
5. Errors: missing database (and the database is still not created afterwards), database with only `example` results, a video as the query, a missing query file. Each raises `SearchError`.
6. CLI run as a subprocess: prints the sample image first and exits 0. With no database it exits 2 and stderr names `snapsort ingest`.
